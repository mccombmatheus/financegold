# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project status

This project is a web app called **FinanGold** (the app's display name — the `<title>`, login screen, and sidebar all show "FinanGold"), built from scratch for "Ipanema Joias" (the multi-store jewelry business whose data it manages: stores include Ipanema, Recreio, Ricardo Angra; companies include Dantas, GPHD, DHD). Don't conflate the two: "FinanGold" is the product name, "Ipanema Joias" is the customer/business the data belongs to. The current source of truth for data is a Google Sheets spreadsheet (a local copy exists at `Fluxo de caixa Ipanema Joias.xlsx` for reference/inspection only — the app talks to the live Google Sheet, not this file). `TESTE MD` is an empty placeholder, not example code. This is not yet a git repository.

### Spreadsheet structure (reference)

- **Lançamento** — the cash-flow ledger (thousands of rows). Columns: Data, Loja, Conta, Empresa, Categoria, Valor, Tipo (Entrada/Saída), Peso (g), Pessoa, Observação.
- **Estoque** — jewelry inventory. Columns: Produto, Tipo, Marca, Condição, Estado, Peso em grama, Pureza (k), Valor de Custo, Valor de venda, Data de Compra, Data de Venda, Comprador, Vendedor, Loja, Vendido?, Observação.
- Lookup/domain tabs (small, list-style — used as dropdown sources): **Pessoa, Contas, Categoria, Lojas, Produto, Tipo de Produto, Marcas, Empresas**. Each entry typically has a numeric code and a "código - nome" complement column used elsewhere as the display value.

## Tech stack

Plain HTML, CSS, and JavaScript only — no frameworks, bundlers, or npm build tooling. Google Sheets integration uses Google Identity Services (OAuth, user login in-browser) plus the Sheets API directly from client-side JS — no backend server. The user already has a Google Cloud OAuth Client ID configured. Development is tested over a local HTTP server (not `file://`, which breaks Google OAuth).

### Multi-company (multi-tenant) routing

The app supports managing several companies' spreadsheets from one login screen, routed by the signed-in Google account's email:

- `js/tenants.js` — `TENANTS`, a plain object mapping an email to an **array** of `{ empresa, spreadsheetId, sheetName }` profiles (one email can manage several companies). This is how "mccomb.matheus@gmail.com → Ipanema Joias → (that company's spreadsheet)" is wired up. To onboard a new company: share its spreadsheet (same tab/column layout as the existing one) with the relevant Google account(s) in Drive, then add/extend that email's entry here.
- **`selectCompanyAndLoadApp` loads Lançamentos, lookups, and Estoque independently** (`Promise.allSettled`, not `Promise.all`) — different companies' spreadsheets can have inconsistent tab structures (discovered when adding a second company whose sheet didn't fully match), so one tab being missing/misnamed degrades that one section instead of blanking the whole app. Failures are collected and shown together in `#status-message` with each underlying error's message, not a generic "something went wrong."
- **Display name + roles, gated by Master — no self-registration**: `js/usuarios.js` manages a `Usuários` tab (Email, Nome, Perfil) inside *each company's own spreadsheet* — not a global/shared directory, since there's no cross-company data store in this architecture. `ensureUsuariosSheet` creates that tab on first use, or upgrades a pre-existing 2-column version from before roles existed (`migrateUsuariosPerfilColumn` backfills any row with a blank `Perfil` to `Master`, since those users already had full access before roles existed — grandfathered in, not guessed).
  - **Access is allow-listed, not self-service.** `js/app.js`'s `resolveProfileAndEnter` looks up the signed-in email in that company's `Usuários` tab. Found → straight into the app as that person (`startApp`, using their stored `Nome`/`Perfil`). Not found *and the tab already has at least one person in it* → `showAcessoNegadoScreen` (`#acesso-negado-screen`), a dead end with only a "Sair" button — there is deliberately no way to grant yourself access. Not found *and the tab is completely empty* → `showCadastroScreen` (`#cadastro-screen`): this is a **one-time bootstrap exception**, since a brand-new company has no Master yet to have added anyone, and `registerUsuario`'s own logic (in `js/usuarios.js`) assigns `Master` only when the tab was empty, `Visualizador` otherwise — so this path can only ever produce the founding Master, never a random signup. Any error while checking access **fails closed** (shows "acesso não liberado" with the error appended, never lets someone in on a fetch failure).
  - **Roles are never displayed as a label anywhere in the app UI** — per explicit user instruction, the tiering stays invisible to end users; it only manifests as which nav items, sections, and buttons exist for them. The Master-only user-management UI lives inside **Ajustes** (see below), not as its own nav item, and is invisible to anyone but Master.
  - **`js/roles.js`** defines the three constants (`ROLE_VISUALIZADOR`/`ROLE_EDITOR`/`ROLE_MASTER`), the global `currentUserRole` (set once in `startApp`), and `canEdit(role)`/`isMaster(role)`. `canEdit` gates: the "Novo lançamento" and "Nova peça" nav subitems (`applyRoleVisibility` in `js/nav.js`, called once per login) and the Estoque action buttons (custody/return/sold — `renderEstoqueActions`'s early return in `js/estoque-ui.js`). `isMaster` gates the `#ajustes-usuarios-section` div inside the Ajustes view (add-user form + a per-row role `<select>` that writes immediately via `updateUsuarioPerfil`, in `js/usuarios-admin.js`).

### Ajustes (settings)

A single nav item, always visible (`data-view="ajustes"`, `#view-ajustes`), holding admin-adjacent cards — internal identifiers still say "ajustes" even though this could theoretically be styled/labeled differently later; keep code and label in sync if renamed again (see the earlier "Fluxo de Caixa" naming note for why this matters).

- **Minha conta** — name/email/company, populated in `startApp` (which now takes a `linha` argument too, tracked as `currentUserLinha` — the signed-in user's own row in `Usuários`, needed to write their edits back to the right place). An "Editar perfil" button (`setupEditarPerfilForm`) reveals an inline Nome + Tipo de perfil form: **Nome is editable by anyone** (`updateUsuarioNome`); **Tipo de perfil is always shown but only enabled for Master** (`tipoSelect.disabled = !isMaster(...)`) — explicit user requirement: the control must stay visible to everyone, never hidden, but a non-Master can't actually change it. The submit handler re-checks `isMaster` before ever calling `updateUsuarioPerfil`, so even a disabled-attribute bypass (e.g. via devtools) can't write a role change — the same UI-gate-not-security-boundary caveat as everywhere else in this feature, just layered twice here since the control is deliberately not hidden.
- **Trocar de empresa** (`#ajustes-trocar-empresa-card`, hidden unless `currentCompanies.length > 1`) — re-shows the company picker for the *same* token (`showCompanyPicker(currentCompanies, accessToken, currentEmail)`), reusing the exact same `resolveProfileAndEnter` path a fresh login would take (including its own access check against the target company's `Usuários` tab) — no separate "switch company" logic to keep in sync.
- **Atualizar dados lives only on the Dashboard now** — a small `.icon-btn` (`#btn-refresh-dashboard`) at the end of the filter row, not a card in Ajustes (removed after the user found the duplication redundant). On click, `refreshAllData()` (in `js/app.js`) disables the button and swaps its label to "Atualizando…" (plain text, no spin/rotation — an earlier CSS spin animation was deliberately removed as "too animated") while it re-fetches lançamentos, lookups, and estoque (reusing `refreshLancamentosAndDashboard`/`refreshEstoque` rather than duplicating their logic) without resetting any view's current filters, plus `refreshUsuariosAdmin()` if Master. Also keeps `estoqueLookups` (a module-level var in `js/estoque-ui.js`) in sync with freshly-fetched lookups — otherwise the custody/sold inline pickers would keep offering a stale `Pessoa` list after a refresh. Its click listener is still wired inside `setupAjustesHandlers` (despite the name) alongside "Trocar de empresa" and "Editar perfil" — that function is really "one-time setup for persistent post-login action buttons," not literally scoped to the Ajustes screen.
- **`#ajustes-usuarios-section`** — the user/role management UI (moved here from a former standalone "Usuários" nav item), gated by `isMaster`.
  - **This is a UI-level gate for workflow, not a real security boundary** (same caveat as `TENANTS`): a Visualizador whose Google account happens to have Drive edit access to the spreadsheet could still write to it outside this app. The actual security boundary remains each spreadsheet's Drive sharing settings; this feature exists so people don't *accidentally* use capabilities they're not meant to, not to stop a determined bad actor.
- **One company → straight into the app; more than one → a picker screen** (`#company-picker-screen`, `showCompanyPicker` in `js/app.js`) lets the user choose which company to work in after login, before `#app-shell` ever becomes visible. `selectCompanyAndLoadApp` is the single place that applies a chosen tenant's `spreadsheetId`/`sheetName` onto `CONFIG` and kicks off the data load — both the auto-select (1 company) and manual-pick (2+) paths call it, so they can't drift apart.
- **This mapping is routing, not the real access control.** The actual security boundary is each spreadsheet's own Google Drive sharing settings — a user's OAuth token can only read/write a sheet if their Google account was separately given Drive access to it. An email present in `TENANTS` but never shared the spreadsheet will still get 403s from the Sheets API; an email absent from `TENANTS` just never gets routed anywhere by this app (harmless either way, since Drive is the real gate).
- `js/auth.js`'s `fetchUserEmail(token)` calls Google's `userinfo` endpoint, which needs the `.../auth/userinfo.email` scope — `CONFIG.SCOPES` in `js/config.js` now requests that alongside `.../auth/spreadsheets`. A session token from before this change won't have it; log out and back in if identity lookup fails.
- **Every sign-in verifies the token actually has every scope in `CONFIG.SCOPES`** (`getTokenScopes` + `hasAllScopes` in `js/auth.js`, checked first thing in `handleSignedIn`) — found necessary because a token can come back with only *some* requested scopes granted (e.g. the account owner unchecked one on Google's consent screen, or a stale session token predates a scope change), and that failure mode is otherwise invisible until every individual Sheets call starts throwing `403 ACCESS_TOKEN_SCOPE_INSUFFICIENT` with no clear cause. On a mismatch the session is cleared and the login screen shows one plain-language message instead of letting three separate fetches fail with cryptic API errors.
- `CONFIG.SPREADSHEET_ID` (and `CONFIG.SHEET_NAME`) are no longer fixed in `config.js` — they start empty and get set onto `CONFIG` at sign-in time in `js/app.js`'s `handleSignedIn`, once the tenant is resolved, *before* any data fetch happens. Every other file still just reads `CONFIG.SPREADSHEET_ID`/`CONFIG.SHEET_NAME` as before — this was a deliberately minimal-footprint change, not a rewrite of the data layer.
- If the signed-in email isn't in `TENANTS`, `handleSignedIn` clears the session token and shows an error on the login screen without ever revealing `#app-shell` — the app shell only becomes visible after a tenant is confirmed.
- The active company's name is shown under the "FinanGold" sidebar title (`#sidebar-empresa`), so a user managing multiple companies always knows which one they're in for that session. There's no in-app switcher to change company without logging out/back in yet — not requested so far, but `showCompanyPicker` already has everything needed if that's wanted later (just re-show it instead of routing straight to `selectCompanyAndLoadApp`).

### Visual design system

Went through **three** iterations with the user — history matters here because the direction changed twice before landing:
1. Sapphire blue + a muted gold secondary accent, gradients, glowing shadows — rejected ("não curti os tons," wanted "mais escuro/sóbrio").
2. One muted, desaturated slate-blue accent (`#2c3e50`), no second hue, restrained shadows — rejected too, but this time as too plain: "O design está ruim... não são somente cores" — the user wanted real typographic hierarchy, richer interaction, and a "fintech/startup" feel, naming Nubank, BTG Pactual, XP, Apple and Samsung as references.
3. **Current, settled direction**, prototyped first as a Design-canvas Artifact (so the user could actually see it before it touched real code — this project's CSS-only iteration had already caused a live bug once, see below) and approved as-is: a confident indigo accent (`#4f46e5`), a light UI with real elevation (soft shadows, hover states), a light sidebar (not dark — iteration 2's fixed-dark-sidebar idea was dropped), a 3-typeface system with real hierarchy, and a functional command palette. If asked to revisit the design again, don't casually reach for iteration 1 or 2's choices (gold accent, dark sidebar, flat slate-blue) — those were each explicitly tried and moved away from.

- **Tokens live in `css/style.css`'s `:root`** (and its `prefers-color-scheme: dark` block): `--color-accent`/`--color-accent-hover`/`--color-accent-wash`, `--color-success`/`--color-success-wash`, `--color-danger`/`--color-danger-wash`, `--hero-bg`/`--hero-text`/`--hero-accent` (the one deliberately dark KPI tile — see below), `--shadow-sm`/`--shadow-md`/`--shadow-accent`, and the three font tokens below. Changing the look starts here. There is no `--color-gold*` or `--sidebar-*` token anymore (both existed in earlier iterations and were fully removed, including every place that referenced them) — don't reintroduce either without the user asking.
- **The sidebar is now a light surface** (`var(--color-surface)`, `var(--color-border)` for its right edge) — it now themes with the rest of the page via the normal light/dark tokens, unlike iteration 2's fixed-always-dark sidebar. The active nav item is `--color-accent-wash` background + `--color-accent` text (a tinted pill), not a filled block.
- **Three-typeface system**, all loaded from Google Fonts (`font-src`/`style-src` extended in the CSP for them): `--font-display` ("Space Grotesk" — page headings, the "FinanGold" wordmark, card `h2`s), `--font-body` ("Plus Jakarta Sans" — everything else UI-text), `--font-mono` ("JetBrains Mono" — every financial figure and KPI number, tabular-figures-style; a deliberate fintech convention so numbers read as precise/data-like, distinct from prose). Playfair Display (iteration 2's serif) is gone.
- **Chart series colors (`--series-*`) were deliberately left untouched** across every iteration — they're the validated, colorblind-safe categorical palette from the dataviz skill (see the Dashboard section above), and swapping them for brand-matching hues would need re-running the palette validator, not a casual edit.
- **Auth screens (`#login-screen`/`#company-picker-screen`/`#cadastro-screen`/`#acesso-negado-screen`) share a split layout**: `.auth-brand` (a dark gradient panel with a dot-grid background, a decorative line-chart SVG, and the wordmark — the full version with headline/stats copy only on `#login-screen` via `.auth-brand-full`/`.auth-brand-copy`; the other three screens get a shorter version with just the logo mark) plus `.auth-panel` (the white form side). The brand panel markup is duplicated across the four screens (this is plain HTML with no templating/includes) — if its copy or styling changes, all four need the same edit; there's no single source to update.
- **KPI tiles** (`js/dashboard.js`'s `buildKpiTile`) now show a real trend percentage ("↑ 12,4% vs. período anterior"), computed in `renderDashboardCharts` by comparing the selected filter range against the immediately-preceding period of the same length (`computeTrend`) — this was shown as a plausible-but-fake number in the design prototype; implementing it for real (not shipping decorative fake data) was a deliberate choice when translating the approved mockup into the app. Returns `null` (tile shows no trend line) when there's no previous-period data or the previous value was zero, rather than a nonsensical or divide-by-zero percentage. The Saldo tile is visually distinct (`--hero-bg` dark card) — a deliberate "the one number that matters most" emphasis, matching the mockup.
- **"Atividade recente" (dashboard) shows real transaction dates, not fabricated relative timestamps.** The design prototype showed "há 12 min" ("12 min ago") style timestamps — the sheet only records a lançamento's transaction date, never when it was entered into the system, so there is no real timestamp to show a relative time for. `renderAtividadeRecente` in `js/dashboard.js` shows the real `Data` value instead. Don't reintroduce fake relative timestamps to match the mockup more literally — that would be showing invented data as if real.
- **The command palette** (`js/command-palette.js`, triggered by the topbar's search-bar-styled button or Cmd/Ctrl+K) is real, working navigation — not decorative chrome copied from the mockup. `COMMANDS` lists every view; `isCommandAvailable` checks the corresponding `.nav-item[data-view]` element isn't role-hidden before offering it, so it can never expose a shortcut to a screen the current role shouldn't see (mirrors `applyRoleVisibility`'s gating). The shortcut is scoped to only fire once logged in (`#app-shell` visible), so it never hijacks Cmd/Ctrl+K on the auth screens.
- **A few fixed, developer-authored SVG icon strings are inserted via `innerHTML`** (`KPI_ICONS` and `ACTIVITY_ICONS` in `js/dashboard.js`) — this is a deliberate, narrow exception to the no-`innerHTML`-with-dynamic-content rule in Security posture below: these strings are constants, never derived from sheet data or user input, so there's no injection surface. Don't extend this pattern to anything that incorporates a variable.
- **Two real bugs found and fixed during the CSS-only (iteration 2) pass, both worth knowing about if the design changes again without a prototype step first**:
  1. **A CSS specificity gotcha**: `.form-actions button` (a descendant selector, specificity 0-1-1) outranks a single class like `.export-btn` (0-1-0) applied to a button that happens to sit inside a `.form-actions` div — e.g. the "Cancelar" button next to "Editar perfil" was rendering with the *primary* button style before `.form-actions button.export-btn` was added to force the secondary look back.
  2. **A shared class styled for only one of its two surfaces**: `.btn-logout` appears on both the sidebar (at the time, dark) and the light auth screens; giving it dark-surface-only colors made it nearly invisible (white-on-white) on the light screens. Now moot since the sidebar is light too and `.btn-logout` has one consistent light-surface style, but the general lesson stands — a shared class used on two different-colored surfaces needs a surface-scoped override, not one flat color set.
- **This iteration was prototyped as an Artifact first, specifically because iteration 2 (CSS-only, no live preview) shipped a real bug** (the invisible button above) despite careful code tracing. The Design-canvas Artifact let the user actually see and approve the direction before any app code changed — recommend the same approach (prototype → approval → implementation) for any future substantial visual change, rather than iterating blind directly on the app's CSS again.
- **Still not verified against a live browser** for the *implementation* itself (no browser-driving tool was available in this environment) — the Artifact prototype was seen and approved by the user, but translating it into `css/style.css`/`index.html`/the JS that builds dynamic markup (KPI tiles, activity feed, command palette) was still done by editing files directly. Have the user actually look at the running app before treating this pass as finished.

### Security posture

There is no backend, so the real access-control boundary is always Google's OAuth + each spreadsheet's Drive sharing settings — everything below is defense-in-depth on top of that, not a replacement for it. Recap for whoever owns the spreadsheets: share each company's sheet only with the specific people who need it (not "anyone with the link"), and keep those Google accounts protected (2-step verification) — that is the actual lock on the data, more than anything in this codebase.

What was audited and confirmed (2026-09, prompted by a user request to harden the app):
- **No XSS sinks.** Every dynamic DOM write in this codebase goes through `textContent`/`createElement`, never `innerHTML` with untrusted content — the only `innerHTML` uses in the whole app are `= ""` to clear a container. No `eval`, `new Function`, or `insertAdjacentHTML` anywhere. This means a malicious value typed into any sheet cell (Observação, a person's name, etc.) renders as inert text everywhere the app displays it, never as executable markup.
- **No formula injection.** All writes go through `updateSheetRow` with `valueInputOption=RAW` (see the earlier note on why), which never interprets a leading `=` as a formula — a cell value like `=IMPORTXML(...)` typed into Observação is stored as literal text, not a live formula. Don't switch any write path to `USER_ENTERED` without re-considering this.
- **No token leakage.** The access token is only ever sent via the `Authorization` header (one unavoidable exception: `getTokenScopes` in `js/auth.js` calls Google's own `tokeninfo` endpoint, which Google's API design requires as a query param — that's Google's endpoint contract, not a choice made here). Nothing logs the token to the console; it lives only in the `accessToken` JS variable and, for session resume, in `sessionStorage` (cleared on tab close, per-tab, never `localStorage`).
- **Added a CSP** (`<meta http-equiv="Content-Security-Policy">` in `index.html`): scripts restricted to `'self'` and `accounts.google.com`, `connect-src` restricted to the specific Google API hosts this app actually calls, `object-src 'none'`. This is defense-in-depth against any *future* injection point, not a fix for a found vulnerability — none was found. `style-src` needed `'unsafe-inline'` because a few spots (`js/charts.js`) set `.style.background`/`.style.transform` directly, which CSP treats like inline styles.
  - **This was not tested against a live browser** (no browser-driving tool was available in this environment) — only reasoned through against the app's actual external dependencies (just the GIS script + the Google API hosts already used). If login or anything else breaks after this change with a CSP error in the console, that's the meta tag being too strict; loosen the specific directive it names rather than removing the whole policy.
  - A `<meta>` CSP is what's available for a plain static file server; if this app is ever deployed behind a real host/CDN, setting the same policy as an actual HTTP response header there would be strictly better (supports `frame-ancestors`, reporting, etc., which the meta-tag form can't do).

A second pass (same request, "teste-as" — actually go looking, not just confirm) found one real, fixable issue and one robustness gap:

- **CSV formula injection — found and fixed.** `js/export.js`'s `toCsvValue` exported sheet fields (Observação, Produto, a person's name...) into `.csv` files verbatim. Excel (and some other spreadsheet readers) treats a cell starting with `=`, `+`, `-`, `@`, tab, or CR as a live formula when a CSV is opened — this is the well-known "CSV Injection" class (OWASP), distinct from the Sheets-side formula-injection point above and *not* covered by the `RAW`-write mitigation, since it's a read/export path, not a write. Anyone with Editor+ sheet access (or a corrupted entry) could plant something like `=HYPERLINK("http://evil.com","click")` in a field that later gets exported and opened in Excel by Master or an Editor. Fixed with `neutralizeFormulaValue` — a value starting with one of those characters gets a leading `'` prepended, which spreadsheet apps read as "force text," so the payload displays as inert text instead of executing. Verified against both malicious inputs and legitimate text that happens to start with `-` (still gets the safe prefix, still correct) using a small Python simulation of the same regex — no JS runtime was available to unit-test the actual file directly.
- **Tenant email lookup didn't normalize case — fixed.** `js/usuarios.js`'s `fetchUsuario` already lowercased/trimmed both sides before comparing emails, but `js/app.js` did a raw `TENANTS[email]` lookup with no normalization. Not an access-control hole (a mismatch fails *closed*, denying a legitimate user rather than admitting an illegitimate one) but a real robustness bug — fixed with `lookupTenants(email)` in `js/tenants.js`, which normalizes before comparing, matching the pattern already used elsewhere. Both call sites in `js/app.js` now go through it; don't reintroduce a raw `TENANTS[...]` lookup.
- **Re-confirmed no open-redirect / URI-injection surface**: no `window.open`, `location.href`/`.assign`/`.replace`, or `javascript:` URI anywhere in the codebase; the only dynamic `.href` assignment (`js/export.js`) points at a `Blob` object URL the app itself created, never at anything derived from sheet data or user input.
- **Still not live-browser-tested** (same limitation as the CSP note above) — for anyone who wants to verify by hand: try entering `<script>alert(1)</script>` or `=1+1` in an Observação field and confirm it renders/exports as inert text, and watch the DevTools console for CSP violation warnings during normal use.

### Offline support

Requested by the user specifically for a power/internet outage scenario: the app should keep showing the last-loaded data, and let new lançamentos/peças entered offline sync automatically once the connection returns.

- **`sw.js`** (project root — a service worker's scope is the directory it's served from, so it has to live at root to cover `/js/*` and `/css/*`) caches the app shell (every HTML/CSS/JS file, listed by hand in `APP_SHELL`) on install, and serves same-origin GET requests cache-first-with-background-refresh. It deliberately **never intercepts cross-origin requests** (`sheets.googleapis.com`, `accounts.google.com`, etc.) — those always hit the network directly, since a cached API response would be stale or wrongly-authorized. Registered by `js/sw-register.js`. Requires HTTPS in production (browsers exempt `localhost` specifically, which is why it works over plain `http://localhost:8080` today).
  - **Bump `CACHE_NAME` whenever you change a cached file's content, and keep `APP_SHELL` in sync with the actual `<script src>` list in `index.html`.** The install/activate handlers only re-fetch and evict old caches when the name changes — editing `css/style.css` or any `js/*.js` file without bumping the version means anyone with the old service worker already installed keeps serving stale content from cache indefinitely. Add any new JS file to `APP_SHELL` in the same change that adds its `<script>` tag.
- **`js/offline.js`** is the shared module everything else below builds on:
  - `isNetworkError(err)` — the load-bearing heuristic for this whole feature. A raw `fetch()` failure (genuinely offline) throws a `TypeError` *before* getting any HTTP response; every error this app throws deliberately is a plain `Error` with its own message (thrown only after checking `response.ok`, i.e. we know we're online and the API said no). So `err instanceof TypeError` reliably means "no connection," never "the server rejected this." Don't reuse this check without keeping that distinction in mind if a new error type is ever introduced elsewhere.
  - **Data cache**: `fetchWithOfflineFallback(fetchFn, cacheName, serialize, deserialize)` runs a live fetch and caches the result (`localStorage`, keyed by `cacheName` + the current `CONFIG.SPREADSHEET_ID` so different companies' caches never mix); on a network-specific failure it falls back to the last cached value instead of throwing, returning `{data, fromCache}` either way. A real API error (permission, bad request) still throws normally — silently showing stale data for a genuine rejection would be worse than an error message. `serializeLancamentos`/`deserializeLancamentos`/`serializeEstoque`/`deserializeEstoque` exist because `.data`/`.dataCompra`/`.dataVenda` are JS `Date` objects, which survive `JSON.stringify` (via `toJSON`) but not `JSON.parse` (comes back as a string) — these convert explicitly both ways. Lookups need no such wrapper (plain data, no dates).
  - **Write queue**: `enqueueWrite(type, payload)` appends to a `localStorage` array (also keyed by spreadsheet), for the two *creation* flows only (see below). `flushQueue()` replays queued items in order on the `online` event (or right after a successful load, if a queue was left over from last time) using the exact same submit functions the live UI uses — `submitLancamentoValues` (`js/form.js`) and `createEstoqueItem` (`js/estoque.js`) — so there is exactly one code path for "create a lançamento," online or replayed. An item that still fails for network reasons stops the flush (keeps the rest queued, order preserved); one that fails for a real API reason is dropped with a visible warning rather than jamming the queue forever.
  - `describeSaveError(err)` — a friendlier "sem internet" message for the handful of actions that are deliberately **not** queued (see below), instead of surfacing a raw "Failed to fetch."
- **What's queued vs. not, and why**: only the two *creation* forms — "Novo lançamento" and "Nova peça" — get offline queueing. Estoque's state-changing actions (mark custody, return to store, mark sold) do **not** queue: they target one specific existing row and read its *current* `Observação`/fields at click time to compute the write; blindly replaying that later, after who-knows-what else may have changed that row in the meantime, risks silently overwriting someone else's intervening edit. A creation is just "add a new row," which has no such conflict — safe to defer. Those un-queued actions instead fail loudly with `describeSaveError`'s "isso precisa de internet" message when offline.
- **Resuming a session while offline is the trickiest part, and was a real bug found while building this**: a `sessionStorage` token from an earlier login can be read with zero network calls, but `handleSignedIn`'s normal path still needs two live round-trips (verify scopes, fetch email) before it knows who's logged in — without a fallback, reloading the page while offline hung forever on "Verificando conta...", unable to ever reach the cached data underneath. Fixed via `js/app.js`'s `saveLastSession`/`loadLastSession`/`enterOfflineFromLastSession`: every successful `startApp` snapshots `{email, spreadsheetId, sheetName, empresa, nome, perfil, linha}` to `localStorage`; if the scope/email checks fail with a network error specifically, `enterOfflineFromLastSession` trusts that snapshot instead of re-verifying it, and proceeds straight into `startApp` (which itself falls back to the data cache as usual).
- **Real limits, stated plainly rather than oversold**:
  - This only works for **up to roughly an hour** after the last successful login — that's the lifetime of a Google OAuth access token in this app's flow (GIS token-client, not a refresh-token flow, by design — see `js/auth.js`), and there's no way to silently renew it without network. A multi-hour outage will eventually require a fresh (online) login.
  - **A first-ever login cannot happen offline** — identifying who you are is inherently a network operation (Google OAuth). Offline support covers "I was already using this app," not "I'm opening it for the very first time with no connection."
  - **No conflict resolution.** Two people offline at once, or someone editing the live sheet while another device is queued, isn't reconciled — last write wins, silently. Acceptable for this app's small-team scale; would need real work to generalize further.
  - **Not tested against a live browser** (no browser-driving tool was available in this environment) — verified by careful code tracing of every path (online, offline-with-cache, offline-with-no-cache, offline session resume, queue flush, partial queue failure) instead. Ask the user to verify with Chrome DevTools → Network → Offline before trusting this in a real outage.

### Running locally

Serve the directory over HTTP (Google OAuth does not work reliably over `file://`):

```
python3 -m http.server 8080
```

Then open `http://localhost:8080`. Before it works, fill in `js/config.js` with a real `CLIENT_ID` (from Google Cloud Console) and `SPREADSHEET_ID` (from the target Google Sheet's URL). The configured OAuth Client ID's authorized JavaScript origins must include the localhost URL/port being used.

There are no lint or automated test commands yet.

### File layout

- `index.html` — two top-level views: `#login-screen` (shown first) and `#app-shell` (sidebar + main content, shown after auth). Only one is visible at a time (`hidden` attribute toggled in `js/app.js`).
- `css/style.css` — all styling, including the login screen, the sidebar layout, and the chart color tokens (light/dark) from the dataviz skill's reference palette.
- `js/config.js` — `CLIENT_ID`, `SPREADSHEET_ID`, sheet name, and OAuth scopes. Not meant to hold real secrets in a shared repo.
- `js/auth.js` — Google Identity Services token client (OAuth in-browser, no backend). Also persists the access token to `sessionStorage` (`saveTokenToSession` / `loadValidTokenFromSession` / `clearTokenSession`) so a page reload in the same tab resumes the session without a new login prompt; closing the tab clears it (that's `sessionStorage`'s native behavior, not custom logic). `signOut()` clears it and revokes the token.
- `js/sheets.js` — thin wrapper around the Sheets API: `fetchSheetValues` (`values.get`, supports `valueRenderOption`) and `updateSheetRow` (`values.update` / PUT on one specific `A{row}:J{row}`-style range, always `valueInputOption=RAW` — see note below).
- `js/lancamentos.js` — fetches and parses the **Lançamento** tab (`fetchLancamentos`); reads with `UNFORMATTED_VALUE` so dates come back as serial numbers (converted via `sheetSerialToDate`) instead of locale-formatted strings. `dateInputToSheetSerial` is the inverse, used when writing a new row. `findNextLancamentoRow` scans column A to find the true next empty row (see note below). `stripCode` strips the leading `"N - "` prefix used throughout the lookup tabs.
- `js/lookups.js` — fetches the small lookup tabs (Lojas, Contas, Empresas, Categoria, Pessoa) that back the lançamento form's dropdowns. Every lookup tab's column C ("Complemento") holds the exact `"N - Nome"` string that `Lançamento`'s own columns store — `toLookupOption` reads that column directly so form submissions stay byte-identical to existing data. `Categoria` is additionally filtered to `Status === "Ativo"`.
- `js/dashboard-data.js` — pure aggregation functions over parsed records: `filterByDateRange`, `computeKpis`, `computeByLoja`, `computeByCategoria`, `computeByMonth`, `topNWithOthers`.
- `js/charts.js` — hand-rolled inline-SVG chart renderers (diverging bar, ranked bar, grouped monthly bar, donut) plus shared tooltip/legend/table-toggle helpers. No charting library dependency, per the vanilla-JS constraint.
- `js/dashboard.js` — wires the date filter (with presets: mês atual/anterior, ano atual, tudo) to the aggregation + chart functions and renders the KPI tiles. `initDashboard` does the first load (sets up filter handlers, defaults to "mês atual"); `updateLancamentos` refreshes the underlying data and re-renders *without* resetting the user's current filter — used after a form submission.
- `js/form.js` — the "Novo lançamento" form: populates the lookup dropdowns, validates, flips the sign of `Valor` based on `Tipo` (Saída is stored negative, matching existing rows), computes the target row via `findNextLancamentoRow`, writes it via `updateSheetRow`, then calls `refreshLancamentosAndDashboard`.
- **One-time setup functions must guard against re-invocation** (`if (xInitialized) return; xInitialized = true;`) — anything wired up inside `selectCompanyAndLoadApp` can run more than once per page load (log out and back in, or pick a different company, without a full page reload), and `addEventListener` doesn't replace a prior listener on the same element, it stacks another one. `setupNavigation`, `setupLancamentoForm`, and `setupEstoqueForm` all follow this; found the hard way when `setupNavigation` didn't and a second login made every submenu toggle button open-then-immediately-close on click (two stacked listeners flipping `hidden` twice per click). If you add a new one-time setup function called from `selectCompanyAndLoadApp`, give it the same guard.
- **Sidebar collapse**: `#sidebar-collapse-btn` toggles `.sidebar.collapsed` — per explicit user request, collapsed means *only* that button stays visible (nav and the user/Sair footer are `display: none`, not shrunk to icons), persisted per-browser in `localStorage` (`financegold_sidebar_collapsed`) via `loadSidebarCollapsedPref`/`saveSidebarCollapsedPref` in `js/nav.js`. There's no way to switch views while collapsed by design — expand first. (An earlier icon-rail-with-flyout-submenu version was built and then deliberately stripped back down to this simpler behavior — don't reintroduce icon spans or a flyout panel unless asked again.)
- **`.sidebar-nav` has no `flex: 1`** — it used to stretch to fill the sidebar's full height, which pinned the footer to the bottom of the viewport and left a large empty gap below just 2-3 nav items. It's sized to its content instead, so the sidebar stays compact with few items and simply grows as more are added — don't re-add `flex: 1` there without re-introducing that gap.
- `js/nav.js` — sidebar view switching (`.nav-item` click ↔ `.view-section` show/hide + topbar title). Add a new view by adding a `.nav-item[data-view=...]` button, a `.view-section[data-view=...]` section, and a title in `VIEW_TITLES`.
- `js/app.js` — orchestrates auth, the two top-level screens (`#login-screen` / `#app-shell`), and kicks off the initial data + lookups fetch on sign-in.

**Why the form doesn't use `values:append`:** the `Lançamento` sheet's dimensions extend to row ~2531 (formatting) even though real data ends around row ~1571, and `values:append`'s "detect the table" heuristic used that whole formatted extent as "the table," landing new rows far past the real data instead of right after it — confirmed by testing. `findNextLancamentoRow` + `updateSheetRow` (a targeted `values.update` PUT) replace that with a deterministic write to the exact next row.

**Why `updateSheetRow` uses `RAW` instead of `USER_ENTERED`:** the sheet stores `Data` as a numeric date serial (see `Lançamento` sheet), and `USER_ENTERED` would depend on Sheets correctly guessing the date format of a plain string, which is locale-dependent and unverified from this codebase. Writing the already-converted serial number via `RAW` matches the existing column's actual representation exactly, so new rows read back identically to old ones. If a future field needs formula evaluation, that field alone would need `USER_ENTERED` (a per-request setting, not per-cell) — reconsider then.

**Known limitation:** `findNextLancamentoRow` + `updateSheetRow` is not atomic — two people saving a lançamento at the same moment could compute the same target row and overwrite each other. Fine for now (single-user usage); revisit if the app gets concurrent users.

### Dashboard (current state)

Implemented: date-range filter (with presets), KPI tiles (entradas, saídas, saldo, ouro comprado, ouro vendido), saldo-por-loja (diverging bar), gastos-por-categoria (ranked bar), entradas/saídas por mês (grouped bar), and two donut charts for top categorias (saídas / entradas). Every chart has a hover tooltip and a "ver tabela" toggle with the same data in plain HTML.

**Gold (Peso/g) moves opposite to the cash `Tipo`**: a "Saída" (cash out) row is the store *buying* gold from someone, so gold comes IN; an "Entrada" (cash in) row is the store *selling*, so gold goes OUT. `computeKpis` in `js/dashboard-data.js` names these accordingly — `pesoComprado` (from Saída rows) and `pesoVendido` (from Entrada rows) — shown as separate "Ouro comprado (g)" / "Ouro vendido (g)" KPI tiles, not netted. Keep this inversion in mind for any future gold/inventory-related feature.

The sidebar has "Dashboard" (flat), a "Fluxo de Caixa" group ("Consultar lançamentos" / "Novo lançamento" — internally `lancamento-lista` / `lancamento-form`; the display name is "Fluxo de Caixa" per the user's naming choice, but files/ids/functions still say "lancamento"), and an "Estoque" group ("Consultar estoque" / "Nova peça"). See `js/nav.js`'s `VIEW_GROUPS`/`openSubmenu`/`toggleSubmenu`, and follow that pattern if a future module also needs a submenu instead of a flat nav item.

- `js/lancamento-lista.js` — the "Consultar lançamentos" table (all columns + row number `#`), filtered by date range (defaults to the full data range), loja, tipo, and free-text search, sorted newest-first. Reuses `computePresetRange`/`toInputDateValue`/`parseInputDate` from `js/dashboard.js` and `populateFilterSelect` from `js/estoque-ui.js` rather than duplicating them. `initLancamentoLista` is called once at sign-in; `refreshLancamentosAndDashboard` (in `js/app.js`) re-renders it too, so a new lançamento shows up here immediately, same as in the dashboard. OAuth scope is read+write (`https://www.googleapis.com/auth/spreadsheets`) — a session token granted under an older read-only scope won't have write access, so log out and back in after pulling a scope change if writes start failing with a permission error.

### Estoque module

- `js/estoque.js` — data layer for the **Estoque** tab (16 columns, A:P — see the header list in that file's top comment). `fetchEstoque` parses every row (each carries `.linha`, its sheet row number, and `.raw`, the original 16-value array — writes always start from a copy of `.raw` with specific indices patched, never reconstructed field-by-field, so a partial update can't accidentally blank out an unrelated column). `findNextEstoqueRow` + a targeted `updateSheetRow` write are used for `createEstoqueItem`, for the same table-detection-heuristic reason documented above for Lançamento.
- **Custody tracking ("com vendedor") uses the existing `Observação` column, not a new one** — this was an explicit user decision (they declined adding a new column to the live sheet). Convention: notes are appended to whatever's already in `Observação`, separated by `" / "` (see `appendObservacao`). The *current* custody state is read from the **last** `" / "`-separated segment only (`parseCustodyFromObservacao` / `computeEstoqueStatus`), matching against `"Com vendedor: <nome>"`; anything else in that last segment (including a fresh `"Retornou à loja"` note) means the piece is back in the store. Don't change this parsing to scan the whole string — only the trailing segment reflects the current state, by design (older notes stay as history).
- **Column convention differs by field**, confirmed against the real sheet data — don't assume every column matches Lançamento's style: `Produto`/`Tipo`/`Marca` store the `"N - Nome"` complemento form (same as their lookup tabs' column C), but `Loja`/`Comprador`/`Vendedor` store the **plain name** (column B of `Lojas`/`Pessoa`, exposed as `lojasPlain`/`pessoasPlain` in `js/lookups.js`) — unlike Lançamento's `Loja`/`Pessoa` columns, which use the complemento form. Mixing these up would silently write data in a format inconsistent with the rest of that column.
- `js/export.js` — `downloadCsv(filename, headers, rows)`, a small dependency-free CSV export (Blob + a throwaway `<a download>`, UTF-8 BOM so accented characters render right in Excel). Both list views export whatever is currently filtered/sorted on screen, not the whole dataset: `exportEstoqueCsv` in `js/estoque-ui.js` and `exportLancamentosCsv` in `js/lancamento-lista.js`. Deliberately CSV, not a real `.xlsx` — that needs a library, and CSV opens natively in Excel/Sheets with zero new dependencies, consistent with the vanilla-JS constraint.
- `js/estoque-ui.js` — the "Consultar estoque" list (filters: loja, status, tipo, free-text search), the sold/custody/return actions (inline panels, not native `prompt()`/modals — `showCustodyPanel` / `showSoldPanel` / `handleReturnToStore`), and the "Nova peça" form.
- **Drag-and-drop reordering is local-only** (another explicit user requirement: don't touch the sheet's row order). `estoque-ui.js` persists the dragged order as an array of `linha` numbers to `localStorage` (`financegold_estoque_order`) and `applyEstoqueOrder` re-sorts by that on every render; it's per-browser, not synced, and items not in a saved order fall back to sheet order at the end.
- **Row numbers ("número de lançamento")**: both `js/lancamentos.js`'s `parseLancamentoRow` and `js/estoque.js`'s `parseEstoqueRow` attach `.linha` (the real sheet row) to every parsed record — requested by the user for both modules. For Lançamento there's currently no per-row list view (only aggregates), so `.linha` only surfaces today in the "Novo lançamento" form's save confirmation ("Lançamento salvo na linha X"); for Estoque it's shown per-card (`#linha`) in the list, since that view is per-item by nature.

Not yet built: views for the other tabs (Contas, Categoria, Pessoa, etc. — these mostly just back dropdowns for now, not their own screens).

## Working conventions

- Treat the Google Sheet as the source of truth for financial/inventory data; do not alter values or the local `.xlsx` reference copy.
- Match new sheet-writing code to the existing column layout/order per tab rather than inventing a new schema, unless the user asks for a structural change.
- Keep OAuth Client ID / Spreadsheet ID out of source in a way the user can supply locally (e.g. a small untracked config), rather than hardcoding secrets into committed files.
